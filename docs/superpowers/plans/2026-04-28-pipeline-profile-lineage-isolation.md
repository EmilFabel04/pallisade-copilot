# Pipeline Profile Lineage Isolation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `pipelineStackId` to the three lineage Prisma models, switch every lineage read and write to scope by `(organizationId, pipelineStackId)`, and verify with tests that two profiles in the same org cannot see each other's lineage.

**Architecture:** A single Prisma migration adds nullable `pipelineStackId` columns to `LineageNode` / `LineageEdge` / `LineageSnapshot`, replaces `LineageNode`'s unique constraint, drops existing rows (dev/demo data only), and adds cascade FKs to `PipelineStack`. The write path (`extract-lineage.ts`) is updated to set `pipelineStackId` on every upsert. The five read paths (lineage GET, lineage DELETE, unified GET, copilot sync, copilot stream) are updated to filter by `pipelineStackId`. Tests assert two-profile isolation at the schema level and route level.

**Tech Stack:** Next.js 15, Prisma, PostgreSQL, Jest + ts-jest.

**Spec:** `docs/superpowers/specs/2026-04-28-pipeline-profile-lineage-isolation-design.md`

- [ ] **Step 2.2: Inspect the generated SQL and add the row-purge step**

Open the new `migration.sql`. Prisma will have produced something close to this, but **without** the `DELETE` lines. After the `ALTER TABLE ... ADD COLUMN` statements and **before** the `DROP CONSTRAINT` for the old unique, insert the destructive purge:

```sql
-- Drop existing rows (dev/demo data only — confirmed by user).
-- Existing rows have pipelineStackId=NULL and would all collide on the new unique constraint
-- if we tried to keep them. Users re-run extraction post-deploy on each profile.
DELETE FROM "LineageEdge";
DELETE FROM "LineageNode";
DELETE FROM "LineageSnapshot";
```

Verify the file ends up structured as:

```sql
-- AlterTable: nullable columns
ALTER TABLE "LineageNode"     ADD COLUMN "pipelineStackId" TEXT;
ALTER TABLE "LineageEdge"     ADD COLUMN "pipelineStackId" TEXT;
ALTER TABLE "LineageSnapshot" ADD COLUMN "pipelineStackId" TEXT;

-- Purge existing rows (intentional)
DELETE FROM "LineageEdge";
DELETE FROM "LineageNode";
DELETE FROM "LineageSnapshot";

-- DropIndex / AlterTable: replace unique
DROP INDEX "LineageNode_organizationId_name_key";
CREATE UNIQUE INDEX "LineageNode_organizationId_pipelineStackId_name_key"
  ON "LineageNode"("organizationId", "pipelineStackId", "name");

-- AddForeignKey
ALTER TABLE "LineageNode"
  ADD CONSTRAINT "LineageNode_pipelineStackId_fkey"
  FOREIGN KEY ("pipelineStackId") REFERENCES "PipelineStack"("id")
  ON DELETE CASCADE ON UPDATE CASCADE;

ALTER TABLE "LineageEdge"
  ADD CONSTRAINT "LineageEdge_pipelineStackId_fkey"
  FOREIGN KEY ("pipelineStackId") REFERENCES "PipelineStack"("id")
  ON DELETE CASCADE ON UPDATE CASCADE;

ALTER TABLE "LineageSnapshot"
  ADD CONSTRAINT "LineageSnapshot_pipelineStackId_fkey"
  FOREIGN KEY ("pipelineStackId") REFERENCES "PipelineStack"("id")
  ON DELETE CASCADE ON UPDATE CASCADE;

-- CreateIndex
CREATE INDEX "LineageNode_organizationId_pipelineStackId_idx"
  ON "LineageNode"("organizationId", "pipelineStackId");
CREATE INDEX "LineageNode_pipelineStackId_idx"     ON "LineageNode"("pipelineStackId");
CREATE INDEX "LineageEdge_pipelineStackId_idx"     ON "LineageEdge"("pipelineStackId");
CREATE INDEX "LineageSnapshot_pipelineStackId_idx" ON "LineageSnapshot"("pipelineStackId");
```

If Prisma's output uses different exact statement ordering, that's fine as long as the DELETE block sits between the column adds and the unique-index drop. The unique-index drop must follow the DELETE because the old constraint must hold while rows exist.
